1Scenario overview

The hypothetical breach this plan responds to, invented for this exercise and loosely modeled on real-world API exposure incidents.

The company

Lumora Retail is a fictional mid-size online retailer with roughly 50 employees and around 120,000 registered customers. It runs a standard web application backed by a REST API, with payment processing handled entirely through a third-party processor so raw card data never touches its own database.

What happened

During a backend refactor, a developer disabled the authentication middleware on the /api/v1/customers/export endpoint to test a new bulk-export feature in a staging branch. That branch was accidentally promoted to production during a routine deploy, and the authentication check was never re-enabled. The endpoint sat publicly reachable, with no login required, for roughly six days before anyone noticed.

What was exposed

  • Full name, email address, and phone number for approximately 120,000 customers
  • Shipping addresses and order history metadata (items, dates, order totals)
  • Bcrypt-hashed passwords (not plaintext)
  • No full payment card numbers — card data was tokenized by the payment processor and never stored locally

2NIST incident response lifecycle applied

The plan below follows the six phases of the NIST SP 800-61 incident handling framework: Preparation, Detection & Analysis, Containment, Eradication, Recovery, and Post-Incident Activity (Lessons Learned).

Phase 1 — Preparation

What should already have been in place

This is what the plan assumes existed (or should have existed) before the breach, since preparation happens before an incident, not during one.

  • A maintained inventory of every public-facing API endpoint, including which ones require authentication
  • An incident response team with named roles: an IR lead, an engineering lead, a communications owner, and a legal/compliance contact
  • Automated monitoring and alerting on API traffic, tuned to flag anomalous outbound data volume, not just downtime
  • Strict separation between staging and production environments, so a staging build cannot silently reach production
  • A published security@lumoraretail.com contact and a basic responsible-disclosure policy, so external researchers have somewhere to report issues instead of posting them publicly
  • Tested backup and restore procedures for the customer database
Phase 2 — Detection & Analysis

How the breach is realistically discovered

Two signals arrive close together. An independent security researcher, who found the endpoint while scanning for exposed APIs, emails security@lumoraretail.com with a handful of sample records as proof and a responsible disclosure note. Around the same time, the on-call engineer notices an unusual spike in outbound bandwidth from the API server on the monitoring dashboard, without an obvious cause.

Initial investigation steps

  • The IR lead is paged and opens a formal incident ticket, classifying it provisionally as High severity pending scope confirmation
  • The researcher's report is verified: the sample records are checked against the production database to confirm authenticity, and the endpoint is reproduced in a controlled, non-production clone rather than touched live in prod
  • API gateway and WAF logs are pulled to establish the exposure window, the requesting IP addresses, request volume, and which fields the responses actually returned
  • Based on the logs, severity is upgraded to Critical once it's confirmed the endpoint had no authentication and had been reachable for six days
Phase 3 — Containment

Stopping the breach from spreading further

  • The /api/v1/customers/export route is immediately disabled via a feature flag at the API gateway, without requiring a full redeploy
  • A WAF rule is pushed to block any request to that path regardless of flag state, as a second layer of containment
  • All active customer session tokens are invalidated as a precaution, in case any were enumerable through the exposed data
  • Access and request logs from the exposure window are snapshotted and preserved before any remediation touches the system, to protect forensic evidence
  • The affected API server instance is isolated from write access to unrelated internal systems while the investigation confirms whether lateral movement occurred (in this scenario, it did not)
Phase 4 — Eradication

Removing the root cause

  • The code path that allowed authentication middleware to be disabled outside of a controlled staging environment is identified and rewritten so that removal of the auth check fails the build
  • A corrected, peer-reviewed build is prepared, with a specific test added that asserts every route under /api/v1/ requires authentication
  • As a precaution, all customer passwords are force-reset even though only bcrypt hashes were exposed, since hashes can still be attacked offline given enough time
  • A check is added to the CI/CD pipeline that blocks any deployment where an API route is missing a required auth decorator or its corresponding test
Phase 5 — Recovery

Safely restoring normal operations

  • The corrected build is deployed through the normal CI/CD pipeline with the new security gate active, not through an emergency manual push
  • The export endpoint is re-enabled gradually, behind authentication, rate limiting, and WAF rules, and is monitored closely for the first 48 hours
  • A focused external re-scan (including a re-test by the reporting researcher, if willing) confirms the endpoint is no longer reachable without valid credentials
  • API traffic and error rates are held under heightened monitoring for 30 days following the fix, with a lower alert threshold than normal
  • The incident ticket is closed only after the IR lead confirms containment, eradication, and recovery steps are all verified, not just deployed
Phase 6 — Post-Incident Activity (Lessons Learned)

What the post-incident review concludes

A blameless post-incident review is held within 5 to 10 business days. It's expected to conclude that the root cause was config drift between staging and production with no automated safeguard against it, and that internal monitoring only caught the anomaly around the same time an external researcher had already found and reported it, which is treated as the more serious gap.

Changes the review is expected to drive

  • Make the CI/CD authentication gate from the Eradication phase a permanent, mandatory part of every deployment, not a one-off fix
  • Physically or logically separate staging and production configuration and secrets so a staging build cannot be promoted by accident
  • Lower the alert threshold for outbound data volume anomalies so internal monitoring would have caught this before an outsider did
  • Formalize the responsible-disclosure process the researcher used informally, into a documented policy with a defined response SLA
  • Run a tabletop incident response exercise quarterly so the team isn't executing this plan for the first time during a real incident

3Internal communication plan

Who gets notified, and roughly when, from the moment the incident is confirmed.

T+0 to 15 minutes
On-call engineer & IR lead
Paged immediately once the anomaly or the researcher's report is confirmed as credible. Incident ticket opened.
T+30 minutes
Head of Engineering & CEO
Briefed on the confirmed scope, severity, and initial containment actions already underway.
T+2 hours
Legal & compliance
Looped in to assess regulatory notification obligations, since customer PII was exposed across an unknown number of jurisdictions.
T+4 to 6 hours
Support & PR teams
Briefed internally with approved talking points, so they can handle inbound questions consistently. No public statement yet at this point.
Within 72 hours
Relevant data protection authority
Notified if legally required once scope is confirmed, in line with the general 72-hour reporting expectation under regulations such as GDPR, subject to legal counsel's guidance for the specific jurisdictions involved.
Within 3 to 5 days
Affected customers
Notified directly by email: what happened, what data was involved, what wasn't exposed (full card numbers), and what action to take (password reset, already enforced).
This is a general internal communication sequence, not legal advice. Actual notification deadlines and requirements vary by jurisdiction and by the specific data protection laws that apply to a real company's customer base.

4Preventative measures

Tied directly to the root cause: an authentication check that was disabled in staging and silently promoted to production.

Measure 1

Add a CI/CD deployment gate that automatically fails any build where an API route is missing its required authentication middleware or corresponding test, so a misconfiguration like this can't reach production undetected again.

Measure 2

Enforce strict separation between staging and production environments, secrets, and feature flags, so a staging configuration can never be promoted to production without an explicit, reviewed step.

Measure 3

Stand up continuous external attack-surface monitoring, or a lightweight formal responsible-disclosure program, so exposed endpoints are caught by the company itself before or at the same time an outside party finds them.
