Executive Summary

This report documents a security assessment performed against a locally deployed instance of OWASP Juice Shop, an intentionally vulnerable web application maintained by the OWASP Foundation for training and educational purposes. The assessment was carried out as part of an internship training cycle to build hands-on proficiency in identifying, exploiting (in a controlled/authorized lab context), and remediating the vulnerability classes described in the OWASP Top 10.

Because Juice Shop is deliberately built with known, catalogued weaknesses for training purposes, the objective of this assessment was not vulnerability discovery in the traditional sense, but demonstration of methodology: mapping the application's attack surface, exploiting each planted weakness using industry-standard tooling, correctly classifying each finding against CWE and CVSS, and documenting remediation guidance to the standard expected of a professional penetration test report.

Approach

The assessment followed a structured black-box methodology against the running local instance:

  1. Reconnaissance and attack-surface mapping — crawling the application through an intercepting proxy to build a complete site map of endpoints, static assets, and client-side code.
  2. Vulnerability identification — manual review combined with targeted automated tooling (SQLMap for injection points, Burp Suite's Intruder/Repeater for parameter manipulation) against each mapped endpoint.
  3. Controlled exploitation — each identified weakness was exploited to the minimum extent necessary to confirm impact (proof-of-concept), consistent with responsible testing practice even in a self-hosted lab environment.
  4. Severity classification — each confirmed finding was scored using the CVSS v3.1 calculator and mapped to its corresponding CWE (Common Weakness Enumeration) identifier for standardized tracking.
  5. Remediation research — for each finding, a concrete, implementable fix is documented, consistent with secure coding practice for the relevant vulnerability class.

Scope

The assessment scope was limited to the OWASP Juice Shop application itself, running locally via Docker, and covered:

  • Public-facing application endpoints (REST API and client-rendered routes)
  • User registration, authentication, and session handling
  • Product search and catalog functionality
  • Shopping basket and checkout/order logic
  • File upload functionality (customer complaint/feedback form)
  • Client-side JavaScript bundles and exposed static assets
  • JSON Web Token (JWT) issuance and validation logic

Out of scope: the underlying Docker host, container runtime, and any infrastructure outside the application container itself, since the objective was application-layer security assessment.

Remediation Summary

General Recommendations

  • Enforce server-side authorization on every request — never trust a client-supplied identifier without validating it against the authenticated session.
  • Replace all fast, general-purpose password hashing (MD5) with a purpose-built, adaptive algorithm (bcrypt, scrypt, or Argon2id) including per-user salting.
  • Apply parameterized queries / prepared statements universally; eliminate all string-concatenated SQL.
  • Implement anti-CSRF tokens on every state-changing request and require re-authentication (current password) for sensitive account changes.
  • Apply strict output encoding and a restrictive Content-Security-Policy to close remaining XSS vectors.
  • Enforce all file upload restrictions (type, size, content) server-side; never rely on client-side/UI-layer restrictions alone.
  • Redesign JWT handling to avoid storing sensitive claims in the payload, use strong signing algorithms, and enforce short expiration windows.

Short Term (address immediately)

  • Finding 1 — Disable directory listing on the web server / static file handler.
  • Finding 2 — Remove sensitive endpoint references and internal comments from client-shipped JavaScript bundles.
  • Finding 5 — Replace MD5 with bcrypt/Argon2id and force a password reset for all existing accounts.
  • Finding 6 — Require current-password re-verification server-side and implement CSRF tokens.
  • Finding 10 — Enforce file type and size validation server-side, independent of any client-side check.

Medium Term

  • Findings 3 & 4 — Migrate all database access to parameterized queries; introduce a SAST rule to flag string-built SQL.
  • Finding 7 — Apply framework-level auto-escaping and a strict CSP; audit all innerHTML/unsafe DOM sinks.
  • Finding 8 — Add object-ownership validation on every basket-related endpoint.
  • Finding 9 — Add server-side quantity bounds validation and re-derive totals server-side rather than trusting client-submitted totals.
  • Finding 11 — Redesign JWT claims and signing configuration; rotate the signing secret.

Long Term

  • Integrate SAST/DAST/SCA scanning into the CI/CD pipeline as a merge-blocking gate.
  • Establish a recurring internal security assessment cadence (quarterly) in addition to periodic external penetration testing.
  • Provide secure-coding training for all contributing developers, focused on the specific weakness classes identified in this report.

Technical Finding Details

1. Directory Listing Exposure

Description

During attack-surface mapping, the intercepting proxy's site map revealed a /ftp directory exposed on the application. Navigating to this path directly returned a raw directory listing rather than a 403/404 response, indicating that directory browsing was enabled on the web server for this path.

[INSERT SCREENSHOT: Burp Suite site map showing the /ftp directory discovered during crawling]

Browsing into the exposed directory listed a set of files available for direct, unauthenticated download.

[INSERT SCREENSHOT: Directory listing of /ftp showing downloadable files]

One of the exposed files, an internal markdown document, contained non-public business information (in this training instance, details framed as company acquisition notes) that should never have been reachable from an unauthenticated, public-facing path.

[INSERT SCREENSHOT: Contents of the exposed sensitive file]

Technical Root Cause

The web server (or static file middleware) was configured to serve directory indexes for a path that also happened to contain files not intended for public access. This is a classic case of a development/staging convenience setting (directory browsing, often enabled for internal file-sharing during development) surviving into a reachable environment.

Impact

Any unauthenticated visitor who guesses or discovers this path can enumerate and download every file placed there, without any access control check. Depending on what is stored in the directory, this can range from low-sensitivity static assets to business-critical documents, credentials, or backup files.

CWE ID: CWE-538: File and Directory Information Exposure

Severity: 7.5 (High)

[INSERT SCREENSHOT: CVSS calculator score breakdown for this finding]

Remediation

  • Disable directory listing/indexing at the web server or static-file-serving layer (e.g., autoindex off; in Nginx, or the framework's static-file middleware configuration).
  • Move any files that must remain on the server but should not be publicly downloadable outside the web root, or behind an authenticated route with proper authorization checks.
  • Run a periodic content-discovery scan (e.g., with a tool such as ffuf or gobuster) against production and staging environments to catch unintentionally exposed paths before an attacker does.

2. Sensitive Information Disclosure in Client-Side JavaScript

Description

Inspecting the application's main client-side JavaScript bundle through the browser's developer tools (using the "pretty print" formatter to de-minify the code) revealed internal implementation details not intended for end users — including references to administrative routes and internal application logic embedded directly in the shipped bundle.

[INSERT SCREENSHOT: De-minified main.js in browser DevTools showing internal route references]

Searching the de-minified bundle for the keyword "admin" surfaced a reference to an administration panel route. Navigating directly to that route exposed an administrative interface, including user records and customer feedback moderation controls, with no additional authentication challenge encountered during testing.

[INSERT SCREENSHOT: Administration panel reached via the route discovered in main.js]

Technical Root Cause

Client-side JavaScript is, by definition, fully delivered to and readable by the end user's browser — it cannot hold secrets. This finding results from security-by-obscurity: the administrative route was not linked anywhere in the normal user interface, and the development team appears to have relied on that lack of a visible link as a substitute for an actual authorization check on the route itself.

Impact

Any user capable of reading their own browser's loaded JavaScript (which is to say, any user) can discover internal routes and application logic never intended for direct interaction. Where the discovered route itself lacks a proper server-side authorization check (as observed here), this becomes a direct path to unauthorized administrative access.

CWE ID: CWE-922: Insecure Storage of Sensitive Information

Severity: 5.3 (Medium)

[INSERT SCREENSHOT: CVSS calculator score breakdown for this finding]

Remediation

  • Never treat "not linked in the UI" as an access control — every sensitive route must independently enforce server-side authentication and role-based authorization.
  • Minify and bundle production JavaScript with source maps disabled/restricted, reducing (though not eliminating) how easily internal structure can be reverse-engineered.
  • Conduct a client-bundle content review as a standard pre-release step, specifically checking for internal comments, route names, or debug artifacts that reveal more than necessary about server-side structure.

3. SQL Injection — Authentication Bypass

Description

The login form's email field was tested for SQL injection by submitting a classic tautology payload — ' OR 1=1 -- — in the email field, with an arbitrary value in the password field. The application authenticated the request successfully, logging the tester in as the first user record in the underlying database (in this application's seeded data, the administrator account).

[INSERT SCREENSHOT: Login form submission with the ' OR 1=1 -- payload]

[INSERT SCREENSHOT: Successful authentication as the admin account following the payload]

To confirm the vulnerability systematically rather than relying on a single working payload, Burp Suite's Intruder tool was configured with a curated wordlist of common SQL injection authentication-bypass strings and run against the login endpoint to identify every variant that succeeded.

[INSERT SCREENSHOT: Burp Intruder attack results against the login endpoint, showing which payloads succeeded]

Technical Root Cause

The login query was constructed by directly concatenating the submitted email value into a SQL WHERE clause rather than using a parameterized query. The injected ' OR 1=1 -- payload closes the string literal early, appends a condition that is always true, and comments out the remainder of the original query (including the password check), causing the query to match every row in the users table and return the first one.

-- Resulting query after concatenation with the malicious input:
SELECT * FROM Users WHERE email = '' OR 1=1 --' AND password = '...'
-- The "--" comments out the password check entirely.

Impact

This is a full authentication bypass requiring no valid credentials whatsoever. Because the query returns the first matching row and the application logic then trusts that row as "the authenticated user," an attacker is not just bypassing login — they are authenticating as whichever account the database happens to return first, which in many seeded/legacy schemas is the administrator.

CWE ID: CWE-89: SQL Injection

Severity: 9.8 (Critical)

[INSERT SCREENSHOT: CVSS calculator score breakdown for this finding]

Remediation

# Vulnerable
query = f"SELECT * FROM Users WHERE email='{email}' AND password='{password_hash}'"

# Remediated — parameterized query
query = "SELECT * FROM Users WHERE email = ? AND password = ?"
cursor.execute(query, (email, password_hash))
  • Migrate all authentication queries to parameterized statements or an ORM's built-in query builder; never concatenate user input into SQL.
  • Add a Web Application Firewall (WAF) rule set as a defense-in-depth layer to flag and block common injection patterns at the network edge, without treating it as a substitute for fixing the underlying query.
  • Add automated regression tests that specifically submit known SQL injection payloads to the login endpoint on every build, failing the pipeline if authentication ever succeeds with a malformed credential.

4. SQL Injection — Data Exfiltration via Search

Description

The product search endpoint was tested for injection using both manual payloads and SQLMap, an automated SQL injection and database takeover tool. SQLMap successfully identified the search parameter as injectable and, once confirmed, was used to enumerate the full database schema.

[INSERT SCREENSHOT: Burp Suite capture of the vulnerable search request/endpoint]

[INSERT SCREENSHOT: SQLMap confirming the injection point and identifying the database engine]

[INSERT SCREENSHOT: SQLMap output listing enumerated database tables]

With schema enumeration complete, SQLMap was directed to dump the contents of two specific tables: a table storing registered payment card records, and the primary user records table. Both were extracted successfully to CSV output.

[INSERT SCREENSHOT: SQLMap dump output for the payment card table]

[INSERT SCREENSHOT: SQLMap dump output for the user records table]

Notably, payment card data was recovered in plaintext, while user passwords were stored in a hashed (though, per Finding 5, weakly hashed) form.

Technical Root Cause

As with Finding 3, the search feature constructs its underlying SQL query via direct string concatenation of the user-supplied search term, rather than a parameterized query. Unlike the login bypass, this injection point allowed full UNION-based data extraction because the search endpoint's query structure was more amenable to appending additional SELECT statements that SQLMap could exploit for arbitrary table access.

Impact

This finding represents the most severe class of outcome for an injection vulnerability: complete, unauthenticated read access to the application's backend database, including financial data (payment cards) stored without encryption. In a production context, this alone would constitute a reportable data breach under most data protection regulations.

CWE ID: CWE-89: SQL Injection

Severity: 9.8 (Critical)

[INSERT SCREENSHOT: CVSS calculator score breakdown for this finding]

Remediation

  • Parameterize the search query exactly as recommended for Finding 3 — this is the same root cause manifesting in a second endpoint, underscoring the need for a codebase-wide audit rather than a per-endpoint patch.
  • Encrypt payment card data at rest (or, preferably, avoid storing raw card numbers entirely by using a tokenized reference from a PCI-compliant payment processor).
  • Apply least-privilege database credentials to the application's runtime database user — a properly scoped account should not have permission to read tables unrelated to its function, limiting the blast radius even if an injection point is missed.

5. Weak Password Hashing Algorithm

Description

Following the database extraction in Finding 4, the recovered password hashes were examined and identified as MD5 digests based on their fixed 32-character hexadecimal length and lack of any salt prefix. The hash set was submitted to CrackStation, an online rainbow-table lookup service, which successfully reversed several of the hashes back to their original plaintext passwords within seconds.

[INSERT SCREENSHOT: CrackStation results showing recovered plaintext passwords from the MD5 hash set]

Technical Root Cause

MD5 is a fast, general-purpose cryptographic hash function designed for data integrity checking, not password storage. It performs no salting and can be computed at extremely high speed on modern hardware (billions of hashes per second on GPU-accelerated hardware), which makes both dictionary attacks and precomputed rainbow-table lookups highly effective. Because no per-user salt was applied, identical passwords across different user accounts also produce identical hash values, further simplifying attack.

Impact

Any breach of the underlying database — whether via the SQL injection in Finding 4, a misconfigured backup, or any other access path — immediately yields plaintext-recoverable credentials for a meaningful fraction of the user base. Because password reuse across services is common, this also creates downstream risk for those users' accounts on entirely unrelated platforms.

CWE ID: CWE-328: Use of Weak Hash

Severity: 9.1 (Critical)

[INSERT SCREENSHOT: CVSS calculator score breakdown for this finding]

Remediation

# Vulnerable
import hashlib
password_hash = hashlib.md5(password.encode()).hexdigest()

# Remediated — bcrypt with per-password salt and tunable work factor
import bcrypt
password_hash = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))
  • Replace MD5 (or any general-purpose hash: SHA-1, SHA-256 used alone) with a purpose-built, adaptive password hashing algorithm — bcrypt, scrypt, or Argon2id — all of which incorporate salting and a tunable work factor by design.
  • Force a password reset for all existing accounts once the migration is complete, since the historical MD5 hashes should be considered permanently compromised.
  • Consider adding a server-side "pepper" (a secret value combined with the password before hashing, stored separately from the database) as an additional defense-in-depth layer against full database compromise.

6. Cross-Site Request Forgery — Password Change

Description

The account password-change functionality was tested for CSRF protection by capturing the change-password request in Burp Suite's Repeater tool and replaying it with modifications. The endpoint expects both the current password and the new password as parameters.

When the current password field was populated with an intentionally incorrect value, the server correctly rejected the request with an error.

[INSERT SCREENSHOT: Password-change request with an incorrect current password, resulting in a rejected/error response]

However, when the current-password parameter was removed from the request entirely (rather than supplied incorrectly), the server processed the request and successfully changed the account password — without ever validating that the requester actually knew the existing password.

[INSERT SCREENSHOT: Password-change request with the current-password parameter omitted, resulting in a successful change]

For comparison, the baseline successful request (correct current password supplied) is shown below.

[INSERT SCREENSHOT: Baseline successful password-change request with the correct current password supplied]

Technical Root Cause

The server-side handler treats the current-password field as optional input to validate if present, rather than as a mandatory precondition for the entire operation. Combined with the complete absence of an anti-CSRF token on the request, this means the endpoint can be triggered by a forged cross-origin request (e.g., an auto-submitting form on an attacker-controlled page that a logged-in victim visits) with no current-password value included, silently changing the victim's password.

Testing note: modern Firefox's default cross-site cookie handling (SameSite defaults) made a live, browser-driven CSRF proof-of-concept harder to reproduce end-to-end during this assessment; the underlying server-side flaw (missing CSRF token, optional current-password check) was nonetheless confirmed directly via Burp Suite Repeater and remains exploitable via other vectors (older browsers, non-browser HTTP clients, or misconfigured CORS).

Impact

An attacker able to lure an authenticated victim to a malicious page (or inject the forged request through another vector) can silently take over the victim's account by resetting their password to an attacker-known value, without ever needing to know the original password.

CWE ID: CWE-352: Cross-Site Request Forgery (CSRF)

Severity: 8.0 (High)

[INSERT SCREENSHOT: CVSS calculator score breakdown for this finding]

Remediation

  • Make the current-password check a mandatory precondition for the entire operation, rejecting the request outright if the field is missing rather than only validating it when present.
  • Implement a synchronizer anti-CSRF token on all state-changing requests (password change, email change, payment method change), validated server-side on every submission.
  • Set SameSite=Strict (or at minimum Lax) on session cookies as a browser-level defense-in-depth control against cross-origin request forgery.

7. DOM-Based Cross-Site Scripting in Search

Description

The product search field was tested with a series of payloads submitted directly into the browser's search bar, targeting the client-side JavaScript responsible for rendering search results into the page DOM.

A baseline payload using a plain <script> tag was submitted first and did not execute, indicating that the application performs some sanitization against literal <script> tags specifically.

<script>alert('XSS');</script>

Result: sanitized — no execution.

However, an <img> tag using the onerror event handler successfully triggered JavaScript execution, demonstrating that the sanitization in place was tag-specific rather than a comprehensive, context-aware output-encoding solution.

<img src=x onerror=alert('XSS')>

Result: successful — alert box triggered.

[INSERT SCREENSHOT: Alert box triggered by the img onerror payload in the search field]

Building on this confirmed sink, additional payloads demonstrated realistic attacker objectives beyond a proof-of-concept alert: a crafted anchor tag that silently redirects a victim to an attacker-controlled page,

<a href="https://attacker.example.com/">Click here</a>

an onerror-triggered redirect requiring no user interaction at all,

<img src=x onerror="window.location='https://attacker.example.com'">

and a payload demonstrating session cookie theft, using an iframe with a javascript: URI to access document.cookie.

<iframe src="javascript:alert(document.cookie)">

[INSERT SCREENSHOT: Cookie value exposed via the iframe/document.cookie payload]

Technical Root Cause

This is a DOM-based XSS vulnerability: the malicious payload never round-trips through the server at all. The client-side JavaScript reads the search term directly from the URL/DOM and writes it back into the page (e.g., via innerHTML or an equivalent unsafe DOM sink) without applying context-aware output encoding. The application's sanitization logic appears to specifically strip <script> tags via a naive filter, but fails to account for the much larger set of HTML attributes and elements (onerror, onload, javascript: URIs, etc.) that are equally capable of executing JavaScript.

Impact

Because this fires entirely client-side, a malicious link containing the payload can be sent to a victim (via email, chat, or a malicious third-party site) and will execute in the victim's authenticated browser session the moment they click it — no server compromise is needed. Demonstrated impact includes session cookie theft (enabling session hijacking) and forced redirection to attacker-controlled phishing pages.

CWE ID: CWE-79: Improper Neutralization of Input During Web Page Generation ('Cross-site Scripting')

Severity: 5.4 (Medium)

[INSERT SCREENSHOT: CVSS calculator score breakdown for this finding]

Remediation

// Vulnerable — unsafe DOM sink
searchResultsElement.innerHTML = userSearchTerm;

// Remediated — safe text insertion; no HTML/JS interpretation
searchResultsElement.textContent = userSearchTerm;
  • Replace unsafe DOM sinks (innerHTML, document.write) with safe alternatives (textContent, innerText) anywhere user-controllable data is rendered.
  • If rich-text rendering is genuinely required, use a dedicated, actively-maintained sanitization library (e.g., DOMPurify) rather than a hand-rolled tag filter — hand-rolled blocklists reliably miss attribute-based and URI-scheme-based vectors, exactly as observed here.
  • Deploy a strict Content-Security-Policy (script-src 'self') as a defense-in-depth layer that blocks inline event-handler execution even if a payload slips past output encoding.

8. Broken Access Control in Basket Operations

Description

Viewing another user's basket: the basket-retrieval request was captured and its endpoint pattern identified as including the target basket's numeric identifier directly in the URL path. The identifier was modified to a different, sequential value than the tester's own basket ID.

[INSERT SCREENSHOT: Original basket-retrieval request showing the tester's own basket ID]

[INSERT SCREENSHOT: Altered request with the basket ID changed to a different, sequential value]

The server returned the full contents of a different account's basket, with no ownership validation performed against the requester's authenticated session.

[INSERT SCREENSHOT: Server response returning another account's basket contents]

[INSERT SCREENSHOT: Application UI reflecting the improperly accessed basket, including the other account's items]

Adding items to another user's basket: a second, related flaw was identified in the "add to basket" flow. Submitting a request with the basket-owning account's own basket identifier behaved as expected.

[INSERT SCREENSHOT: Baseline add-to-basket request using the authenticated account's own basket ID]

Simply changing the basket ID value to a different account's ID had no effect — the server appeared to validate the primary parameter. However, submitting the request with a duplicated basket-ID parameter (the legitimate one, plus a second one pointing at a different account) resulted in the item being added to the second, unauthorized basket.

[INSERT SCREENSHOT: Altered request with a duplicated basketId parameter pointing to a different account]

[INSERT SCREENSHOT: Successful response confirming the item was added to the unauthorized basket]

[INSERT SCREENSHOT: Application UI confirming the item now appears in the other account's basket]

Technical Root Cause

Both sub-findings share the same root cause: the server trusts a client-supplied object identifier (basket ID) without verifying it belongs to the authenticated session. The parameter-pollution variant (duplicated basketId parameter) further suggests that request parsing and the authorization check are not applied to the same resolved value — likely because whichever parameter instance the parsing layer resolves first differs from the one the business logic ultimately acts on, a common and easy-to-miss class of bug in frameworks that silently accept duplicate parameters.

Impact

Both read and write access-control failures are present: any authenticated user can view another user's basket contents (a privacy violation exposing another customer's purchasing activity) and can modify another user's basket by adding unwanted items — a functional integrity violation that, in a real e-commerce context, could be used for harassment, order manipulation, or as a pivot toward more damaging fraud.

CWE ID: CWE-284: Improper Access Control

Severity: 8.1 (High)

[INSERT SCREENSHOT: CVSS calculator score breakdown for this finding]

Remediation

  • Scope every basket query and mutation to the authenticated session's own user/basket ID server-side, regardless of what identifier value the client submits.
  • Reject requests containing duplicate instances of the same parameter name, or explicitly define and test which instance the framework resolves, rather than leaving it to implicit, framework-default behavior.
  • Add automated authorization tests ("can User A access User B's resource?") as a standard part of the endpoint test suite for every object-scoped route.

9. Improper Input Validation on Basket Quantity

Description

The basket-update request was captured and its quantity parameter modified to a negative integer value.

[INSERT SCREENSHOT: Original basket-update request with a normal positive quantity]

[INSERT SCREENSHOT: Altered request with the quantity parameter set to -10]

The server accepted the negative quantity without validation error and updated the basket accordingly.

[INSERT SCREENSHOT: Successful response confirming the negative-quantity update]

[INSERT SCREENSHOT: Basket UI displaying a negative total price as a result]

Proceeding through checkout with the negative-quantity basket, using the application's built-in digital wallet payment method, resulted in funds being credited to the tester's wallet balance rather than debited — effectively the inverse of a normal purchase.

[INSERT SCREENSHOT: Order confirmation showing the negative total processed through the digital wallet]

[INSERT SCREENSHOT: Wallet balance increased following the negative-total "purchase"]

Technical Root Cause

The total-price calculation (unit_price × quantity) is computed without any server-side bounds check on the quantity value, and the resulting negative total is passed through to the payment/wallet logic without a sanity check confirming the amount is a valid, positive charge. This is fundamentally a design gap, not merely a missing input filter: the business logic never establishes an invariant that a "purchase" must always result in a non-negative transaction amount.

Impact

Direct financial impact: an attacker can repeat this transaction to arbitrarily inflate their wallet balance, effectively generating funds from nothing. In a production payment system, this is a critical business-logic flaw capable of causing direct monetary loss at scale, well beyond what a typical technical CVSS score alone communicates to non-technical stakeholders.

CWE ID: CWE-20: Improper Input Validation

Severity: 6.5 (Medium) — reflects technical exploitability; the business/financial impact should be communicated separately to stakeholders as high-priority regardless of the technical CVSS score.

[INSERT SCREENSHOT: CVSS calculator score breakdown for this finding]

Remediation

# Vulnerable — no bounds check
total = unit_price * quantity

# Remediated — explicit invariant enforcement
if quantity < 1 or quantity > MAX_QUANTITY_PER_ITEM:
    raise InvalidQuantityError("Quantity must be a positive integer within allowed limits")
total = unit_price * quantity
if total <= 0:
    raise InvalidOrderError("Computed order total must be a positive amount")
  • Enforce a strict positive-integer bounds check on quantity server-side, independent of any client-side UI restriction (e.g., a spinner control's minimum value).
  • Re-derive and validate the order total entirely server-side at checkout time — never trust a client-submitted total, and never allow a checkout to proceed if the computed total is not a sane, positive value.
  • Add explicit business-logic test cases (negative quantity, zero quantity, extremely large quantity) to the checkout test suite.

10. File Upload Restriction Bypass

Description

The customer complaint/feedback form includes a file attachment feature with front-end enforced restrictions: a maximum file size of 100 KB and an allow-list limited to .pdf and .zip extensions.

[INSERT SCREENSHOT: UI rejecting a file over the 100 KB limit]

[INSERT SCREENSHOT: UI rejecting a file with a disallowed extension]

Extension bypass: a shell script (payload-script.sh) was renamed with a trailing allowed extension (payload-script.sh.zip) to pass the front-end's extension check.

[INSERT SCREENSHOT: The renamed file passing the front-end extension check]

[INSERT SCREENSHOT: Confirmation that the renamed file was accepted by the application]

Combined bypass via request interception: to fully restore the original malicious filename and exceed the size limit simultaneously, the upload request was intercepted with Burp Suite before it reached the server. The filename field within the multipart form data was edited back to the true payload-script.sh extension, and additional padding data was appended to the request body to exceed the 100 KB front-end limit.

[INSERT SCREENSHOT: Original intercepted multipart upload request]

[INSERT SCREENSHOT: Altered request with filename restored and size limit exceeded]

The server processed the altered request and accepted the upload, confirming that both the extension allow-list and the size limit were enforced only in the browser, with no equivalent check applied server-side.

Technical Root Cause

Both restrictions (file type, file size) exist exclusively as client-side JavaScript validation on the upload form. The server-side handler that ultimately writes the uploaded file to storage performs no independent verification of the file's actual extension, MIME type/content, or byte size — it implicitly trusts that any request reaching it has already passed the front-end's checks.

Impact

An attacker can upload arbitrary file types and sizes, including executable scripts. Depending on where uploaded files are stored and how they may later be accessed or executed by the server or other processes, this can range from a denial-of-service risk (unbounded storage consumption) to full remote code execution if the upload path is ever reachable/executable by the server or a downstream process.

CWE ID: CWE-434: Unrestricted Upload of File with Dangerous Type

Severity: 8.8 (High)

Remediation

Technical Root Cause

Two distinct design weaknesses combine here. First, the JWT payload includes sensitive account attributes directly as claims — while JWTs are commonly (and correctly) treated as signed but not encrypted, this application appears to rely on the token's contents remaining private, which is an incorrect trust assumption for a format that any holder can freely decode. Second, and more critically, the server's token validation logic failed to reject a token with its alg field removed and no signature present — indicating either an alg: none acceptance vulnerability or a validation routine that does not enforce presence of a valid signature before trusting the payload's claims.

Impact

The signature-stripping bypass is a complete authentication and authorization control failure: it allows an attacker who has captured any single valid token to forge a token asserting any user identity, without needing that user's credentials, a valid signature, or the signing secret. Combined with the plaintext-readable claims, this also constitutes an information-disclosure issue independent of the tampering vulnerability, since any holder of a legitimate token (including, e.g., a token logged inadvertently by an intermediary proxy) can read another user's email and role directly.

Remediation

# Vulnerable — algorithm accepted from the token itself, no explicit allow-list
decoded = jwt.decode(token, key, algorithms=jwt.get_unverified_header(token)['alg'])

# Remediated — explicitly pin the expected algorithm; never trust the token's own header for this
decoded = jwt.decode(token, key, algorithms=["HS512"])  # explicit allow-list, "none" never accepted
  • Explicitly pin the accepted signing algorithm(s) on the server side (e.g., HS512) rather than deriving the expected algorithm from the token's own, attacker-controllable header — this is the standard root-cause fix for alg: none and algorithm-confusion style bypasses.
  • Avoid placing sensitive attributes (email, role) directly in JWT claims where avoidable; where they must be included, treat the token as fully readable by its holder and design accordingly (never rely on claim confidentiality for security decisions).
  • Enforce short token expiration windows and implement server-side revocation/rotation capability, since JWTs are otherwise valid and unrevokable for their full lifetime once issued.
  • Store the signing secret in a dedicated secrets manager, rotate it periodically, and use a sufficiently long, random key appropriate for the chosen HMAC algorithm.
